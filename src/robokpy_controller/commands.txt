The fix was exactly what we suspected: rclpy.spin_until_future_complete(self, future, executor=self.executor_ref, ...) was deadlocking because it tried to spin an already-spinning MultiThreadedExecutor from within a callback running on that same executor.
Replacing it with a simple polling loop let the existing executor threads process the service response on one thread while the callback blocked on another.
Summary of the fix:

# BEFORE (deadlocks):
rclpy.spin_until_future_complete(
    self, future, executor=self.executor_ref, timeout_sec=5.0)

# AFTER (works):
start = time.monotonic()
while not future.done() and time.monotonic() - start < 5.0:
    time.sleep(0.01)

real rule is simpler and stricter: never call spin_until_future_complete from inside a 
callback already running on the executor doing the spinning, full stop


Where it's genuinely fragile right now:

    Today's bug count skewed heavily toward concurrency bugs, not domain logic — executor deadlocks, reentrancy anti-patterns, thread starvation. That's a signal, not a coincidence: the pattern of "block synchronously inside a service callback by manually managing futures/threads" is workable but inherently brittle in rclpy. I'd seriously consider whether anything that waits on physics/topics (spawn, attach, despawn) should be its own action server instead of a blocking service — actions give you the async lifecycle for free instead of hand-rolling it, which is where most of today's bugs actually lived.
    grasp_attach_bridge's real attach/detach path (not the diagnostic one we hardened in object_spawner) still has zero physical confirmation — it reports success on message-publish, not on confirmed weld. That's a known, documented gap, but it means the actual recipe-facing grasp path doesn't have the same reliability guarantee we just spent real effort building elsewhere.
    approach_offset is one empirically-measured constant, not derived from real geometry. Fine as a pragmatic unblock, but it won't transfer to a different gripper without re-measuring by hand — worth a real calibration routine or mesh-based derivation eventually.
    Vision is entirely unexercised — the actual "pick where a camera tells you" loop has never run once. Everything validated today is a fixed, known pose. That's the single biggest unknown for real-world readiness.
    The bounded catalog is a real ceiling, not just a current limitation — fine at confirmed scale, but it's a wall, not a slope, if requirements ever grow past it.

Bottom line: this reads as a strong pre-v0.1 research/education-grade system with genuinely good bones — better architected than most projects at this stage — but not yet industrial-production-grade. The gap isn't the design, it's reliability engineering: real integration tests (even one headless-Gazebo smoke-test recipe in CI) would have caught several of today's bugs before they ever reached a live session, and closing the concurrency-pattern class of bug systematically (rather than one deadlock at a time) would do more for "industrial-grade" than any new feature at this point.

f you need to create meshes for a custom robot
The standard ROS 2 workflow is:

    Visual meshes — Export high-resolution models from CAD (.stl, .dae, .obj) for RViz/Gazebo rendering.
    Collision meshes — Create simplified, convex versions of those meshes (target < 500 triangles per link) or use primitive shapes (box, cylinder, capsule) for stable physics. 

URDF/Xacro — Reference both in your robot description:
xml

    <link name="example_link">
      <visual>
        <geometry><mesh filename="package://my_robot/meshes/visual_link1.stl"/></geometry>
      </visual>
      <collision>
        <geometry><mesh filename="package://my_robot/meshes/collision_link1.stl"/></geometry>
      </collision>
    </link>

    Validation — Use tools like yourdfpy or check_urdf to verify inertia tensors and mesh paths before launching in ROS 2.

If you can share a link to the robot, a photo, or the correct name, I can point you to the exact files or help you generate them.
